1. What we can handle today

The foundation is Go/Fiber, PostgreSQL, a Next.js dashboard, Better Auth, and an Apps Script Gmail add-on. A Caddy edge service provides one public origin and routes requests to the private dashboard and API. Keep this architecture; richer analytics does not require replacing Go or introducing a separate analytics platform immediately.

2. Shortcomings against mature trackers—and what we can offer

Mature trackers commonly provide open summaries, link metrics, document engagement, reminders, CRM outcomes, exports, and filters for automated activity. Their pixels still face the same privacy and caching limits. We should compete through useful workflows, transparent evidence, and ownership of data rather than claiming perfect read receipts.

3. Define statuses and metrics before building charts

Replace a single overloaded status with four independent dimensions. A message can be sent, have unknown delivery placement, show proxy image activity, and later produce a verified conversion.

  • Sending: prepared, pending, accepted-by-Gmail, failed, unknown. Preserve existing API states for compatibility and explain their meaning in the UI.
  • Delivery evidence: unknown, bounce-reported, or delivery-report-received where genuine evidence exists. Do not turn “no bounce” into “delivered.”
  • Engagement: image activity, link activity, document activity, reply detected. These can coexist; no activity means no activity detected.
  • Outcome: none, manual goal recorded, webhook goal recorded, reversed/refunded. A manual mark is not a provider-verified outcome.

Prepared add-on drafts, failed sends and unknown sends are excluded from sent-based rates until reconciled. Group-mode sends count as deliveries, not as individually observed recipients. Report prepared drafts in a separate activity cohort. Empty denominators display “Not enough data.” Store timestamps in UTC and render in the chosen reporting timezone. Cohorts use send date; events use explicit observation windows.

5. Repeat opens, IP addresses, user agents, and FingerprintJS

Can a second open generate a second request?

Yes—when the mail client actually fetches the image again. Log those requests and show repeated detected activity. But caching may reuse the image without contacting us; background/privacy fetches may contact us before a person opens the message. Cache-control headers help at our endpoint but cannot force every mail client or proxy to refetch.

Gmail protects image loading from exposing the recipient's computer/location; Apple Mail Privacy Protection can hide IPs and download remote content in the background. Therefore repeat requests cannot establish “read exactly twice,” and absence of a second request cannot establish “opened only once.” Gmail image behavior; Apple privacy behavior.

What to implement

  1. Separate raw bounded request observation from session aggregation. Remove the current five-minute suppression from the source-event layer; retain a versioned session rule in analytics. Keep quotas, coalesced counters and overflow markers to prevent abuse.
  2. Capture server receive time, delivery ID, event type, source, request method, parsed browser family where useful, and evidence flags. Treat provider-image proxies as proxy observations, not identifiable devices.
  3. Resolve IP only through a verified proxy chain. Test Railway → Caddy → Go forwarding; the API remains private and Caddy must overwrite/normalize client-controlled forwarded headers. Do not trust the leftmost X-Forwarded-For blindly.
  4. Default to minimized network data: short-lived diagnostic raw IP only if enabled; otherwise keyed HMAC/truncated network information with a documented retention window. Pseudonymous hashes are still sensitive and are not a person ID.
  5. Use flags such as known-image-proxy, suspected-link-scanner, owner-preview, unknown-source and unclassified. Store classifier version/reasons. Do not invent a percentage probability that someone read the email.

IP plus user agent is a weak grouping signal: shared networks, VPNs, mobile network changes and identical browsers cause collisions and splits. Country/ASN lookup can offer approximate network context for direct browser visits; do not present precise location, identity, or reliable Gmail recipient location.

Where FingerprintJS fits

Ordinary email bodies cannot run the browser JavaScript needed by FingerprintJS. It can run on our hosted document viewer or a landing page we control. Prefer first-party sessions first. If an opt-in experiment later uses @fingerprintjs/fingerprintjs, pin and review the package, pseudonymize its visitor ID, restrict collection to the viewer, and label the result “estimated browser.” Never use it for access control or claim it identifies a person. The project itself documents spoofability and accuracy limitations. FingerprintJS repository.

6. Track clicked links

For dashboard sends, parse sanitized HTML using an HTML parser. Rewrite eligible HTTP/HTTPS anchors into /c/{opaqueToken}, with a distinct token per delivery and logical link. Persist the validated destination before sending. Keep mailto/tel, unsubscribe/preferences links, existing tracked URLs, and signed or one-time links out unless explicitly supported. Plain-text alternatives should use the corresponding tracked URLs too.

  1. The composer offers “Track links,” shows which destinations will change, and lets the sender exclude individual links.
  2. The send preparation transaction creates link records and token hashes. Reuse these records on idempotent retry; never generate a second set for the same attempt.
  3. The public redirect resolves the token to a stored destination, checks active/expiry state, records a bounded observation, and issues a non-cacheable 302.
  4. The destination receives no recipient email or raw delivery ID. The capability URL identifies the delivery server-side.
  5. Distinguish raw GET requests, suspected scanners, and estimated click sessions. HEAD requests do not count as clicks. Browser user agents alone do not prove human activity.

Use stored destinations rather than an arbitrary ?url= redirect. Restrict schemes and reject credentials/control characters. The redirect never needs to fetch the destination, avoiding SSRF through preview fetching. Disabling tracking should stop logging while preserving navigation for legitimate old emails where safe; explicit document revocation is a separate access action.

Gmail add-on phase one: generate a tracked link the user inserts manually. Phase two: investigate compose APIs and draft-body permissions in a focused spike before promising automatic rewriting. The current insert-pixel action does not provide a full draft rewrite pipeline. Show “Links not instrumented” on these messages until supported.

Security tools can follow links automatically; filters reduce noise but cannot eliminate it. Mailchimp bot-activity guidance.

7. Track PDFs and images through hosted shares

A native PDF/image attachment can be downloaded, cached, opened offline, or forwarded without any request to us. We cannot reliably measure those opens. Offer an explicit “Send as tracked document link” option alongside normal attachments.

Storage and access

  • Create a durable document library with immutable file versions, owner ID, object key, checksum, MIME type, size, page count and status. Do not reuse disposable composer-file cleanup.
  • Use an S3-compatible private bucket for hosted documents; a separate persistent volume is acceptable for an initial single-replica pilot. Add object deletion jobs, backup/restore and quotas.
  • Create per-delivery shares with high-entropy hashed tokens, expiry, revocation and download policy. A share URL grants access; forwarding also forwards access unless recipient authentication is enabled.
  • Exchange the URL capability for a short-lived viewer session and redirect to a clean URL. Use HttpOnly/Secure session cookies, restrictive referrer policy and no third-party viewer analytics.
  • Offer optional verified-email access when recipient identity matters. This adds friction and requires a matching recipient policy; a browser fingerprint is not authentication.

PDF and image viewer

Use a self-hosted PDF.js integration for PDFs and a controlled image viewer for supported image formats. Record viewer_loaded only after rendering succeeds. Record page exposure when at least 50% of a page is visible for a defined interval, and foreground activity in bounded ten-second heartbeats. Pause when hidden or idle. Define page coverage as qualifying distinct pages divided by document page count.

Show viewer sessions, revisits, pages exposed, approximate active time, download requests, and optional verified identity. Do not call scroll coverage “read completion.” A successful file response or Range fetch is not a new view. Download clicks indicate a request, not confirmed saving or later offline reading. Image zoom/pan can be optional interaction metrics without claiming visual attention.

Reject HTML/SVG or serve unsafe formats only as downloads from an isolated origin; allowlist MIME/signature combinations, scan uploads, limit file/page sizes, patch the renderer, and use a restrictive CSP. Prevent one document's JavaScript or embedded actions from reaching the dashboard session. No native-PDF beacon tricks.

8. Gmail state, reply detection, bounces, and spam

Useful Gmail/account state

Settings should show connected, needs reconnect, token refresh failed, add-on paired, read sync enabled, last successful sync, and sync delayed/error. Do not mistake a missing event for a disconnected mailbox. Send state and Gmail account health belong in different UI components.

Optional read synchronization

Keep send-only mode usable. Add a separately enabled “Sync replies and delivery reports” feature that requests the minimum verified scope for the selected work. Header/label-only workflows may use gmail.metadata; parsing bounce content or rendering message bodies requires broader read access. Both metadata and readonly are restricted scopes, and public server-side processing introduces Google verification/security-assessment requirements. Validate the intended deployment category before shipping broadly. Google scope reference.

  1. Store granted scopes and capability state per mailbox. Reconnect only when the user enables features requiring more access.
  2. Start with durable scheduled incremental polling and a saved Gmail history cursor. Limit initial sync to relevant threads/time windows; handle expired history cursors with a bounded full resync.
  3. Correlate using mailbox + Gmail thread ID, RFC Message-ID, In-Reply-To and References. Thread membership alone is insufficient for individual recipient attribution.
  4. Exclude outgoing/self mail, recognized auto-replies and bounce reports from human reply counts. Preserve ambiguous attribution for shared sends.
  5. Parse genuine DSN/bounce reports conservatively: recipient, action, diagnostic/status and referenced message. Record bounce-reported, not invented deliverability.
  6. Later add Gmail watch → Cloud Pub/Sub → authenticated push endpoint. Renew watches on a schedule and retain polling reconciliation; notifications trigger history fetches rather than containing full messages.

For add-on sends, “prepared” remains the truth until a reliable Sent match exists. A scope-limited spike must prove how to correlate a prepared draft with its sent message using a supported draft identifier or narrowly scoped body matching. Subject/recipient/time similarity alone is ambiguous; it must not silently mark sent. If matching is unavailable, retain prepared and exclude from sent-rate denominators.

Introduce threads and messages as separate entities. Existing conversation IDs represent send attempts; preserve their URLs and optionally add a thread view grouping multiple attempts plus incoming messages. Do not merge unrelated historical sends just because subjects match.

Can we tell whether a recipient got the email in spam?

Not for arbitrary recipients through our sending Gmail account or tracking pixel. The sender's SPAM label concerns the sender's mailbox, not the recipient's placement. A missing open cannot diagnose spam.

A later seed-testing feature can send to controlled test inboxes and inspect their labels/folders. Report “seed inbox placement” by provider, with sample size and time—not the actual customer's folder. Add SPF/DKIM/DMARC checks and, where authorized and available, aggregate Google Postmaster domain signals. These are diagnostic context, not per-message guarantees.

9. Conversion rate that means something

Define goals such as reply received, meeting booked, form submitted, qualified lead, purchase, or manually marked won. Use server-confirmed outcomes for bookings/purchases whenever possible. A landing-page visit is engagement, not automatically a conversion.

  1. Create a goal with a stable ID, event name, default attribution window (proposed: 30 days), and value/currency policy.
  2. On a tracked destination we control, carry an opaque attribution reference into a first-party session. Cross-domain destinations need an explicit integration; a redirect alone cannot observe their purchases.
  3. Record events through authenticated server webhooks: signature verification over the original body, timestamp/replay checks, size limits, idempotent external event IDs and tenant/owner binding.
  4. Keep manual outcomes separate, including actor, recorded time and an audit trail. Support reversals/refunds without erasing original evidence.
  5. For MVP, choose the last eligible tracked click before the conversion within the goal window. Store the attribution policy and matched evidence; require timestamps that precede the conversion.
  6. Keep unattributed conversions rather than forcing matches by email or IP. Shared and forwarded links retain “attributed delivery,” not proven clicker identity.

Show goal conversion rate over eligible sent deliveries, plus a separate click-to-conversion rate over eligible clicked deliveries. Deduplicate orders by provider event/order identity; don't sum mixed currencies without explicit conversion rules. Freeze or version report policies so changing the window/filter does not silently rewrite historical results.

These examples explain the design; they are illustrative, not complete production patches. Interfaces, migrations, configuration, authorization and integration tests must be implemented together.

Go: redirect observation without accepting arbitrary destinations 
package trackinghttp

import (
    "context"
    "crypto/sha256"
    "encoding/base64"
    "net/url"
    "time"

    "github.com/gofiber/fiber/v3"
)

type Link struct {
    ID, DeliveryID, Destination string
    LoggingEnabled bool
}
type Links interface {
    ResolveActive(context.Context, []byte) (Link, error)
    RecordRequest(context.Context, Link, time.Time) error
}

func Redirect(repo Links) fiber.Handler {
    return func(c fiber.Ctx) error {
        raw, err := base64.RawURLEncoding.DecodeString(c.Params("token"))
        if err != nil || len(raw) != 32 {
            return c.SendStatus(fiber.StatusNotFound)
        }
        hash := sha256.Sum256(raw)
        ctx, cancel := context.WithTimeout(c.Context(), time.Second)
        defer cancel()
        link, err := repo.ResolveActive(ctx, hash[:])
        if err != nil { // Production: distinguish not-found from DB outage.
            return c.SendStatus(fiber.StatusNotFound)
        }
        dest, err := url.Parse(link.Destination)
        if err != nil || dest.Hostname() == "" || dest.User != nil ||
            (dest.Scheme != "https" && dest.Scheme != "http") {
            return c.SendStatus(fiber.StatusGone)
        }
        if c.Method() == fiber.MethodGet && link.LoggingEnabled {
            // Atomic bounded insert + outbox. Instrument failures;
            // a logging failure should not prevent valid navigation.
            _ = repo.RecordRequest(ctx, link, time.Now().UTC())
        }
        c.Set("Cache-Control", "no-store")
        c.Set("Referrer-Policy", "no-referrer")
        return c.Redirect().Status(fiber.StatusFound).To(dest.String())
    }
}

Generate 32 random bytes with crypto/rand; store only their SHA-256 hash. ResolveActive validates expiry/owner relationships server-side. Add method restrictions, quotas, trusted-proxy metadata and error counters in the real handler. Redact capability tokens from edge/access logs.

SQL: conversion rate counts deliveries rather than orders 
WITH eligible AS (
  SELECT id, confirmed_sent_at
  FROM deliveries
  WHERE owner_id = $1                 -- proposed owner-bound schema
    AND confirmed_sent_at >= $2
    AND confirmed_sent_at < $3
    AND source <> 'test'
), converted AS (
  SELECT DISTINCT a.delivery_id
  FROM conversion_attributions a
  JOIN conversions c ON c.id = a.conversion_id
  JOIN eligible e ON e.id = a.delivery_id
  WHERE c.owner_id = $1 AND c.goal_id = $4
    AND c.reversed_at IS NULL
    AND c.occurred_at >= e.confirmed_sent_at
    AND c.occurred_at <= e.confirmed_sent_at + $5::interval
    AND c.occurred_at <= $6             -- explicit report cutoff
    AND a.policy_version = $7
)
SELECT count(*) AS eligible_deliveries,
       count(*) FILTER (WHERE c.delivery_id IS NOT NULL) AS converted,
       100.0 * count(*) FILTER (WHERE c.delivery_id IS NOT NULL)
         / NULLIF(count(*), 0) AS conversion_rate
FROM eligible e LEFT JOIN converted c ON c.delivery_id = e.id;

The attribution table stores the selected eligible click and policy. Bound goal window values in the API. This query targets the proposed model; the existing deliveries table does not have all these fields.

JavaScript: bounded foreground telemetry in our hosted viewer 
// Viewer session already established in a Secure, HttpOnly cookie.
// The bootstrap endpoint returns a session-bound CSRF value.
export function startViewerTelemetry(csrf, getVisiblePages) {
  let last = performance.now();
  let lastInput = last;
  let activeMs = 0;
  const touch = () => { lastInput = performance.now(); };
  const inputs = ['pointerdown', 'keydown', 'wheel', 'touchstart'];
  inputs.forEach(name => window.addEventListener(name, touch, {passive:true}));

  const timer = setInterval(() => {
    const now = performance.now();
    const elapsed = Math.min(now - last, 1500);
    last = now;
    if (document.visibilityState !== 'visible' || now - lastInput > 30000) {
      return;
    }
    activeMs += elapsed;
    if (activeMs < 10000) return;
    const payload = {
      batchId: crypto.randomUUID(),
      kind: 'viewer_activity',
      activeMs: Math.round(activeMs),
      pages: getVisiblePages() // IntersectionObserver-derived page numbers
    };
    activeMs = 0;
    void fetch('/api/v1/viewer/events', {
      method: 'POST', credentials: 'same-origin', keepalive: true,
      headers: {'Content-Type':'application/json', 'X-CSRF-Token':csrf},
      body: JSON.stringify(payload)
    }).catch(() => {}); // Best effort; no invented time after failed delivery.
  }, 1000);

  return () => {
    clearInterval(timer);
    inputs.forEach(name => window.removeEventListener(name, touch));
  };
}

The server derives share/delivery/owner from the session, validates Origin/CSRF, caps activeMs per batch and session wall time, validates page bounds and deduplicates batchId. Client telemetry is forgeable: present approximate active time. This code runs in our browser viewer, never inside Gmail. Add page-exposure thresholds and rendering-success events separately.

13. Implementation phases and acceptance criteria

Suggested complete scope: approximately 12–18 engineering weeks, plus external OAuth verification or integration approval time. These are planning ranges, not delivery commitments. Gmail synchronization and document work can be scheduled independently after the foundation.

Phase 0 · Foundation and evidence contract · 1–2 weeks

Build: event taxonomy, metric definitions, confirmed-send timestamps, instrumentation version, additive migrations, legacy import, token-log redaction, proxy-chain validation, rate limits, outbox/jobs, pagination design and observability.

Acceptance: legacy timeline remains accessible; no fabricated history; raw vs deduplicated data is identifiable; duplicate jobs/events are idempotent; crash/restart drains committed outbox; spoofed forwarded headers cannot become trusted recipient IPs.

Phase 1 · Conversation analytics and repeat activity · 1–2 weeks

Build: summary/event APIs, keyset pagination, basic classifier flags, first/last activity, estimated sessions, delivery selector, overview/timeline/diagnostics UI and detail SSE invalidation.

Acceptance: totals are independent of timeline page size; prepared/failed/unknown are excluded from sent metrics; shared attribution is explicit; proxy events remain visible but distinguished; empty denominators and unavailable instrumentation do not show misleading zeroes.

Phase 2 · Dashboard link tracking · 1–2 weeks

Build: anchor rewriting, plain-text parity, per-delivery link tokens, redirect handler, edge routing, per-link analytics, exclusions and manual add-on link insertion.

Acceptance: separate deliveries have distinct tokens; shared mode stays aggregate; query strings/fragments and signed-link exclusions work; HEAD/scanner observations do not inflate eligible counts; retries do not duplicate tokens; logging failures preserve valid navigation; expired/invalid destinations are safe.

Phase 3 · Hosted PDFs and images · 2–3 weeks

Build: durable object storage, document library/versioning, per-delivery shares, clean-URL viewer sessions, PDF.js/image renderer, page visibility/active time, expiry/revocation and download policies.

Acceptance: native attachments remain available; sending cleanup cannot delete library documents; Range requests do not inflate views; hidden/idle tabs stop accruing time; revoked shares fail; authenticated identity is distinct from estimated sessions; malicious/oversized files are rejected or isolated.

Phase 4 · Manual outcomes and conversion integrations · 1–2 weeks

Build: goals, audited manual outcomes, one selected booking/form/purchase integration, signed webhook intake, deduplication, attribution windows and conversion cards.

Acceptance: replayed provider events count once; unsigned/wrong-owner events fail; conversion evidence remains distinct from click telemetry; reversals are reflected; unattributed events are preserved; counts and money do not multiply through SQL joins.

Phase 5 · Optional Gmail reply/bounce sync · 2–3 weeks plus approval time

Build: scope/capability UX, read-access reconnect, incremental polling, history-cursor recovery, message/thread entities, reply matching and bounce parsing. Add Pub/Sub/watch only after polling works.

Acceptance: send-only users keep working; revoked access yields a reconnect state; duplicate/out-of-order sync notifications are harmless; self/auto-replies are excluded; shared replies remain ambiguous where necessary; prepared drafts are not falsely marked sent.

Phase 6 · Reports, reminders and production hardening · 2–3 weeks

Build: mailbox/campaign/cohort reports, CSV export, documented metric policies, manual follow-up reminders, retention cleanup, restore drill and performance tuning. Establish SLOs from pilot measurements.

Acceptance: reports reconcile with delivery drill-down; date/timezone boundaries work; deleting a conversation/document follows documented retention; exports neutralize spreadsheet formula injection; load tests and replica notification tests meet agreed targets.

Later, separately scoped: seed inbox testing, Postmaster integration, automated sequences, CRM connectors, team roles, A/B experiments, opt-in browser fingerprint study, and analytics infrastructure beyond PostgreSQL. None blocks the initial conversation/link product.

14. Testing, rollout, and migration verification

  • Domain tests: metric denominators, session windows, classifier rules/versioning, forwarding/shared attribution, conversion windows, reversals and reply classification.
  • PostgreSQL integration tests: concurrent token fetches, summary consistency, idempotency, cursor boundaries, owner isolation, job lease recovery and legacy backfill.
  • HTML/MIME tests: parser rewriting, malformed markup, duplicate/signed links, plain-text parity, preserved reply headers, individual vs shared tokens and attachments.
  • Viewer tests: render failures, visible-page thresholds, hidden/idle time, duplicate telemetry, forged page/time fields, expired sessions, byte-range access and download policy.
  • Webhook/sync tests: signature/replay verification, duplicate/out-of-order provider notifications, stale history cursor, OAuth revocation, quota/backoff and ambiguous sent reconciliation.
  • Client matrix: controlled Gmail web/mobile, Apple privacy on/off, Outlook, image blocking, cached reopening, forwarded mail and security-scanned links. Measure behavior empirically rather than promising universal counts.

15. Privacy, security, and operational reliability

Collect only data needed for the selected feature. Proposed configurable defaults: diagnostic raw IP off, or maximum seven days when explicitly enabled; detailed activity 90 days; pseudonymous session data 90 days; rollups 12 months; hosted files retained until owner deletion or configured expiry. These are product defaults to review, not legal retention claims. Explain tracked documents/analytics to users and provide collection controls, exports and deletion.

  • Never expose Gmail refresh tokens, pairing codes, capability URLs, raw IPs or message bodies in generic logs. Store encryption secrets separately from database backups and test key-loss recovery planning.
  • Apply owner authorization to every dashboard object and nested resource. Public viewer access is share-scoped; document sessions must not gain dashboard privileges.
  • Rate-limit by token/session/network with global bounds. Record overflow counters and data-coverage warnings; never silently present a capped count as a full lifetime total.
  • Use structured safe error codes: pairing_code_invalid_or_used, addon_identity_mismatch, mailbox_reconnect_required, instance_unavailable. A backend/database failure must not masquerade as expired pairing. Show actionable recovery; retain diagnostics server-side.
  • Use a transactional outbox for notifications and summaries. The current in-memory SSE broker does not fan out across API replicas; start with one replica or introduce PostgreSQL LISTEN/NOTIFY/pub-sub invalidation with reconnect refetch.
  • Do not blindly turn sending into a retrying job: an uncertain Gmail response can hide a successful send. Persist attempt states, reconcile evidence and require review before repeating ambiguous sends.
  • Monitor ingestion latency/errors, dropped/coalesced events, summary lag, redirect availability, viewer failures, worker backlog, sync age/watch expiry, webhook rejects and object-storage costs.

Make the product's own follow-up reminders suppressible after reply/outcome. If automated sending is added later, implement durable scheduling, cancellation, unsubscribe handling and provider rate limits before enabling sequences.

16. Recommended decisions and the first sprint

Proceed with these defaults: keep Go + Next.js + PostgreSQL; extend the existing conversation route; ship dashboard links first; use hosted document links for attachment analytics; make Gmail read sync optional; use first-party sessions before fingerprinting; report click/reply/conversion rates with explicit cohorts; and treat spam placement as a later controlled seed-test feature.

  1. Write the event/status/metric contract and examples in the repository; agree on labels for raw, estimated, proxy and legacy data.
  2. Add confirmed_sent_at, instrumentation metadata, activity events, rollup/outbox tables and a resumable legacy backfill.
  3. Validate trusted proxy metadata and redact tokens in access logs; add bounded ingestion and failure/overflow counters.
  4. Add analytics and paginated event contracts, regenerate clients, and implement owner-scoped queries.
  5. Upgrade the existing detail page with summary cards, a paginated timeline, delivery selection and evidence explanations.
  6. Run controlled reopen/cache/privacy tests and compare new summaries in shadow mode before switching the default UI.
First usable release: a richer conversation detail page plus dashboard link tracking. It answers “what activity did we observe, when, against which delivery and link?” The next release adds hosted document engagement and goals; optional Gmail sync adds verified replies and reported bounces when permissions permit.
